唯讀審查日期：2026-07-30　｜　repo：D:\失竊調查表\taitung-theft

目的：找出最值得建立 deep module、清楚 seam、改善 locality 與 testability 的架構位置。

執行摘要

目前專案是一個以 GitHub Pages 提供的單頁 HTML 工具，功能集中在 index.html。主要風險不是檔案數量少，而是同一份案件資料與計算規則被 DOM、global state、Firebase、Google Sheets、列印模板與 Excel Open XML 實作同時理解。最值得先處理的是把計算規則與案件草稿模型放在穩定 seam 後，再逐步拆 UI 與 adapter。

建議第一項：ARCH-01 損失／復舊計算的重複邏輯。它可以用小範圍、純函式的 deep module 先建立可靠的 test surface，並降低 UI 列印與 Excel 結果分歧的風險。

候選項目詳細證據

ARCH-01 計算規則在三個輸出面重複 P0

高影響中工作量建議首先處理
目前問題

同一組 loss、restore、points、accessory、labor、travel、misc 與 total repair 規則沒有單一 interface。UI 即時計算、HTML 列印與 Excel model 各自讀取資料並計算，未來公式修正容易只改到其中一處。

實際證據
  • index.html:2035-2084：calcAll() 從 DOM 與 DB 計算 loss totals。
  • index.html:2261-2323：generatePrintArea() 重新建立 items 與完整 repair 公式。
  • excel-report.js:133-160：collectReportModel() 再次計算同類數值。
改善方向

建立純的 LossCalculator module，interface 可收 ReportDraft、material catalog 與費率設定，回傳一個完整 LossBreakdown。UI、print renderer、Excel model builder 都只消費這個結果；DOM 更新留在 UI adapter。這個 seam 有直接的 production caller 與 test caller，不需要為了抽象而增加空 port。

影響範圍

calcAll、generatePrintArea、collectReportModel、Excel download、相關測試與既有數值相容性。

風險與驗證

最大風險是既有四捨五入、預設工資／工時與 Excel 欄位結果改變。先用目前 fixture 建立 characterization tests，再逐欄比對 UI、列印與 Excel model；不要一開始改公式。

ARCH-02 案件草稿沒有 canonical model P0

高影響高工作量
目前問題

表單值分散在 DOM、_lossRows、_meterRows、global DB 與各種 localStorage。儲存時才由 DOM 組合資料，還原時又反向操作 DOM 並依賴多個 setTimeout。這使「表單目前狀態」不是一個可獨立測試的 module。

實際證據
  • index.html:1192-1236：collectFormData() 直接讀取欄位、dynamic row 與 option DOM。
  • index.html:1396-1483：loadToForm() 直接寫回 DOM，並以多層 setTimeout 重建 rows。
  • index.html:1854-1957：dynamic rows 由 global arrays 與 DOM id 雙重維護。
改善方向

定義 ReportDraft module，interface 僅處理 read、update、serialize、hydrate 與 validation；DOM 只作為 renderer / input adapter。歷史紀錄、Excel、列印都接收同一個 draft snapshot。先保留 Firestore 文件欄位名稱，降低資料 migration 風險。

影響範圍

表單輸入、動態材料列、草稿儲存／還原、列印、Excel、歷史紀錄編輯。

風險與驗證

既有資料含 dbIdx 與 name 的 fallback 邏輯，切換時不可只依 index。需測試空值、材料刪除或重排、舊文件還原與自訂下拉選項。

ARCH-03 單一 HTML 巨型 module 與混合事件模型 P1

廣泛影響高工作量
目前問題

index.html 同時包含 CSS、頁面 markup、Firebase orchestration、catalog sync、表單 calculation、CRUD、列印模板、checklist 與 mobile navigation。事件又混用 inline handler、動態產生的 inline handler 與 addEventListener，global function 因而成為隱含 interface。

實際證據
  • index.html 共 2,849 行，沒有 source module 目錄。
  • index.html:350-374、2778-2844：大量 markup inline onclick。
  • index.html:1894-1906、2133：render function 產生含 inline event 的 HTML。
  • index.html:1366-1384：歷史紀錄則改用 addEventListener，形成兩套事件路徑。
改善方向

採增量拆分：先把 LossCalculator、ReportDraft、ReportRepository 形成深 module，再把 print、Excel、catalog adapter 移出 inline script。事件統一由 screen controller 或 delegation 綁定；不以「每個函式拆一檔」為目標，而以穩定 interface 和 locality 為目標。

影響範圍

所有 tab、dynamic rows、mobile nav、列印與歷史紀錄操作。

風險與驗證

拆分期間最容易出現 script loading order、global name 與 DOM id 斷裂。每次只移動一個 seam，配合 browser smoke test；本輪不建議直接大重構。

ARCH-04 Firebase CRUD 與 UI 混合，client PIN 不是 authorization seam P0

資料與安全風險中至高工作量
目前問題

畫面函式直接建立 Firestore query、寫入、更新、刪除與錯誤訊息；編輯／刪除前的 PIN 只由瀏覽器 hash 比對後決定是否呼叫操作。repo 內沒有 Firebase Rules 或 auth policy 文件，因此無法從程式碼確認 server-side authorization 是否存在。

實際證據
  • index.html:1252-1258：saveReport() 直接 db.collection('reports').doc().set()。
  • index.html:1306、1400、1535、1552、1582、1627：多處直接 CRUD / query。
  • index.html:1176、1492-1518：EDIT_PIN_HASH 與 requirePin() 完全位於 client。
改善方向

建立小而深的 ReportRepository interface，讓 UI 只知道 save、list、get、updateEditableFields、remove 等 domain operation。production 使用 Firestore adapter，測試使用 in-memory adapter。真正的權限應由 Firebase Auth / Rules seam 保證，client PIN 只能作 UX gate，不應作安全保證。

影響範圍

填報、歷史、草稿、無失竊回報、月初提醒與 Firestore Rules／部署設定。

風險與驗證

這項若涉及 Rules 是高風險部署工作。先盤點實際 Rules、Auth provider、匿名／登入身份與既有資料讀寫需求，再設 repository contract；不可在沒有 production policy 證據時直接收緊規則。

ARCH-05 catalog 的 source of truth 與同步策略不清 P1

資料一致性中工作量
目前問題

DB 可能來自預設值、localStorage cache 或 Google Sheets CSV；同步還會經過 direct fetch 與多個 CORS proxy。使用者在 UI 修改價格後只寫 localStorage，但 manual sync 又能以遠端資料覆蓋 global DB。UNITS 則是另一套 localStorage-only 路徑。

實際證據
  • index.html:1708-1710：loadDB()、loadUnits() 與 global state。
  • index.html:1766-1792：遠端 CSV 與 proxy fallback。
  • index.html:1795-1803：manualSync() 直接替換 DB 並重建 UI。
  • index.html:2114-2123、2139：價格與服務所資料各自寫 localStorage。
改善方向

建立 CatalogStore module，明確定義 loadSnapshot、refresh、saveLocalEdits、freshness 與 conflict policy。Google Sheets CSV、localStorage 與測試 fixture 是不同 adapter；UI 只收到 immutable snapshot，不直接改 global DB。

影響範圍

價格表、表單下拉選單、計算、同步 badge、離線 fallback 與使用者本機編輯。

風險與驗證

不能假設 Google Sheets 是唯一真相；需先決定本機修改是否允許、何時被覆蓋、離線資料保存多久，再補同步狀態與 fixture tests。

ARCH-06 Excel model 與 Open XML / browser download adapter 綁定 P1

中影響中工作量
目前問題

excel-report.js 同時包含 domain model 建立、工作簿載入、XML cell 操作、sheet mapping、formula clearing、Blob 產生與瀏覽器下載。model builder 又依賴 global DB，未傳入資料 catalog 時還會 fallback 到 global collectFormData()。

實際證據
  • excel-report.js:133-160：collectReportModel() 做 domain aggregation 並讀 global DB。
  • excel-report.js:165-308：template / XML / sheet 變更與 workbook configuration。
  • excel-report.js:309-339：Blob、Object URL、anchor click 與 filename。
  • tests/excel-report.test.js:1-39：測試需手動注入 window 與 DB，只覆蓋 model，未覆蓋 template adapter。
改善方向

保留外部的 downloadExcelReport 作薄 facade，內部拆成 ReportModelBuilder（純資料、可測試）與 ExcelTemplateAdapter（XML mapping、template loader、download sink）。template loader 與 download sink 可在測試使用 fixture / fake adapter，讓 adapter 的錯誤模式變成明確 interface。

影響範圍

Excel 報表、模板 sheet 名稱／cell mapping、檔名與瀏覽器下載流程。

風險與驗證

Open XML 的 sheet name、defined name、print area 與 formula 行為容易受影響。先增加 fixture-level XML assertions，再移動實作；不可只依現有 model test 判定 Excel 輸出正確。

建議處理順序

  1. 先處理 ARCH-01：抽出純計算 module，保留既有輸出格式，補 characterization tests。這是最小 seam、leverage 最高、可獨立驗證的切入點。
  2. 接著處理 ARCH-02：讓所有輸出消費同一個 ReportDraft snapshot，再處理 DOM 與 persistence。
  3. 之後依需求選擇：若資料權限或歷史紀錄風險較急，優先 ARCH-04；若價格常變或離線使用重要，優先 ARCH-05；若 Excel 模板頻繁變更，優先 ARCH-06。
  4. 最後進行 ARCH-03 的增量拆分：它是結構性改善，不建議在沒有前述 seam 的情況下直接把 2,849 行切成許多 shallow modules。

本輪結論與限制

  • 本輪只讀取 repo、執行既有 Excel model test，沒有修改任何既有程式碼。
  • HTML 報告本身是本輪新增的檢查產物；它不代表任何架構改善已經實作。
  • Firebase Rules、部署設定與實際瀏覽器流程不在 repo 內，因此 ARCH-04 的 server-side authorization 是待確認的風險，不是本次已證實的 Rules 缺陷。
  • 請從 ARCH-01 至 ARCH-06 選擇一項；在你選擇前不會修改程式碼。
